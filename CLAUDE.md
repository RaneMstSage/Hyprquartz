## Paths

- hyprutils port: subprojects/hyprutils

## What this port is
This is a FAITHFUL PORT. Upstream is the specification.
1. Everything ports: every file, function, class, enum, option, comment and line.
2. NEVER cut, drop, skip, stub or simplify anything because it "looks unused", "isn't needed yet" or "can be added later".
3. Only Linux/Wayland-specific parts change (Wayland, aquamarine, DRM/KMS, libinput, GLES/EGL, XWayland, systemd, Linux-only syscalls/headers). Each gets an EXPLICIT, NAMED macOS replacement. "Drop" is not a replacement.
4. Linux-specific behavior is porting work, not a note. Anything that works differently or silently stops working on macOS needs a macOS replacement.
5. For any real Linux/Wayland code or Linux-only API: STOP, describe what it does upstream, propose the replacement, wait for approval.
6. A Linux-derived name with no Linux code behind it (e.g. applyFromWlr, AQ_FORMAT_*) ports verbatim without stopping; list it in the file's report.
7. Do not fix or improve upstream, including typos and suspected bugs. Report suspected bugs; port as-is.
8. Keep upstream comments verbatim. Add no comments of your own. Match upstream formatting.

## Corner-cutting is forbidden
- Leaving anything out because you judge it unimportant, unused, legacy, debug-only, test-only or Linux-only.
- Porting a subset of enum values, #defines, overloads, members, functions, options, keywords, test cases or #if branches.
- Removing an overload because another "covers it".
- Stubbing: empty bodies, TODOs, placeholder returns, #if 0, (void) where upstream has real code.
- Abbreviating: "rest unchanged", "etc.", summarizing instead of writing the file.
- Simplifying, merging, reordering, renaming, or swapping upstream helpers for std:: equivalents.
- Deleting comments, upstream copy-paste mistakes included.
- Skipping error handling, asserts, logging or edge cases.
If a file is too long for one response, stop at a clean boundary and say where. If you think "not needed", "skip", "for now" or "simplified", stop and ask.

## Evidence rule
Every claim about macOS behavior needs evidence: a quoted macOS man page, an SDK header path and line, an Apple documentation URL, or an approved test result. Otherwise label it UNVERIFIED and say how to verify it. Never conclude "this can't work on macOS" from an unverified claim. "It doesn't work on macOS" is never a final answer; the feature still ports with a macOS replacement that keeps upstream's inputs, outputs and failure cases.

## Config contract
hyprland.conf (hyprlang) and hyprland.lua (Lua 5.5, hl.* API) stay identical: same option names, types, defaults, keywords, dispatchers and Lua functions. Options with no macOS meaning still register and parse without error. Implementation may diverge; the interface may not.

## Naming rule
- Names other programs look up stay Hyprland's: HYPRLAND_INSTANCE_SIGNATURE, HYPRLAND_CMD, .socket.sock, .socket2.sock, hyprland.conf, hyprland.lua.
- Names that identify the program become Hyprquartz: binary, log files (hyprquartz.log / hyprquartzd.log), banner, --version output.

## Known macOS limitations
- FileDescriptor.cpp isClosed() on a named FIFO: XNU only exposes "all writers have gone" through select() while the buffer is empty and before the first EOF read (implemented). Linux's POLLHUP in the other cases cannot be reproduced on macOS. Measured with probes/poll/poll_probe.cpp: Q5, a writer wrote then left with data unread (Linux closed=true readable=true; macOS closed=false readable=true); Q6, EOF already read once (Linux closed=true readable=false; macOS closed=false readable=false). Evidence: XNU fifo_vnops.c fifo_close_internal / fifo_read, vfs_vnops.c filt_vnode_common. Re-check with probes/poll/poll_probe.cpp. The eventLoop Kqueue.cpp replacement has the same gap (same XNU cause, same PollMask rule). Measured with probes/eventloop/eventloop_probe.cpp: Q5, Linux R/RW [R|HUP], W [HUP]; macOS R/RW [R], W []. Q6, Linux [HUP] for R, W and RW; macOS []. Every other named-FIFO state (Q1–Q4, Q7, Q8, and Q2 including the transition while blocked, V1/V1w, and the drain case V8) matches Linux.

- Named FIFO write end after the last reader closed (Q9): XNU exposes no state for it. Measured with probes/poll/poll_probe.cpp: kqueue write filter fires with data=8192 and no EV_EOF, read filter none, select(W)=1, poll() POLLOUT only. Linux reports POLLERR: FileDescriptor::isClosed() is true there, and the event loop reports ERR (R) / W|ERR (W, RW). On macOS isClosed() is false and the event loop reports W without ERR. An anonymous pipe's write end (P3) is not affected (EV_EOF/POLLHUP present, results match Linux). A write to the FIFO still fails (EPIPE, UNVERIFIED, not measured). Re-check with probes/poll/poll_probe.cpp and probes/eventloop/eventloop_probe.cpp (row Q9).

- AF_UNIX stream socket whose peer closed while data this end wrote was still unread (S4, a reset): Linux sets ECONNRESET on this end and the event loop reports ERR with HUP (R [R|HUP|ERR], W [W|HUP|ERR]). macOS keeps no trace of it: the socket state is identical to a plain peer close (proc_pidfdinfo soi_state 0x2030, soi_error 0, same as S1 and L1; kqueue EV_EOF with fflags 0), so the Kqueue.cpp replacement reports HUP without ERR. FileDescriptor::isClosed() is not affected (true on both). Measured with probes/poll/poll_probe.cpp and probes/eventloop/eventloop_probe.cpp (row S4).

- pty master after the slave wrote and closed (T8): macOS discards the slave's unread output when the slave closes (FIONREAD 0, kqueue read data 0 on the master), so FileDescriptor::isReadable() is false and the event loop reports HUP / W|HUP without R. Linux keeps the data: FIONREAD 1, poll POLLIN|POLLOUT|POLLHUP, isClosed()=true isReadable()=true, event loop R [R|HUP], W [W|HUP], RW [R|W|HUP]. Measured with probes/poll/poll_probe.cpp and probes/eventloop/eventloop_probe.cpp (row T8).

- Event loop source on /dev/tty (kqueue cannot attach, EV_ERROR EINVAL; PollMask kind TTY_SELECT) whose descriptor is closed without removeFD and /dev/tty is then reopened at the same number: the Kqueue.cpp replacement cannot tell the two apart (no kqueue filter to lose; fstat identity is the same vnode), so the registration continues on the new open file. On Linux and with upstream Kqueue.cpp the registration belongs to the open file and is dropped (Linux: epoll(7); not measured here, UNVERIFIED). Only reachable by closing a descriptor the loop owns ("The event loop takes ownership of fd", EventLoop.hpp) without removeFD.

- Event loop source on a pipe or FIFO whose descriptor is closed without removeFD and the number is reused by another pipe before the kqueue worker notices: macOS gives the new pipe the same identity (fstat st_dev 0 and the same st_ino, measured in probes/eventloop/eventloop_probe.cpp row Z4), so the Kqueue.cpp replacement's identity check cannot tell them apart and the registration can follow the new pipe. A presence check on the backend's own kqueue filter would detect it (ENOENT after close and after reuse, rows F2 j and F3 b), but on macOS touching a filter re-evaluates it: EV_ENABLE|EV_RECEIPT and EV_RECEIPT alone both re-trigger the EV_CLEAR event and replace its udata (rows F1 d, F2 c and h, F4 c), which would busy-loop in wait(), so it is not used. In the measured run nothing was delivered (Z4), because close() removed the kqueue filters and the worker dropped the select() watch on EBADF before the reuse. That outcome depends on timing. Reuse by a different kind of file is detected. Only reachable by closing a descriptor the loop owns without removeFD.

- eventLoop cost per callback (always-ready source, P0 write end with W, probes/eventloop/eventloop_probe.cpp C1/costbreak): the Kqueue.cpp replacement takes 38.5 us wall / 28.3 us CPU per callback, upstream Kqueue.cpp on macOS 32.6 / 22.6, Linux Epoll.cpp 0.51 us (different hardware). Most of it is upstream's design: every dispatch() does a worker round trip (30.4 us per empty dispatch, row CB2, same for upstream); porting keeps that structure. The replacement adds about 6 us: two shared-kqueue state queries (4 kevent, 3.95 us), the fstat identity check (2 fstat, 2.5 us) and one extra notify write, from computing the mask at requeue and again at delivery (so stale state is never reported). No result depends on it; only throughput for always-ready sources.

- Numeric.hpp float/double parsing below macOS 26: Apple's libc++ has no floating-point from_chars there, so strToNumber<float/double/long double> uses upstream's own strtod fallback (Numeric.hpp:49-77, enabled via _LIBCPP_AVAILABILITY_HAS_FROM_CHARS_FLOATING_POINT). strtod follows the process's LC_NUMERIC: man 3 strtod, "The decimal point character is defined in the program's locale (category LC_NUMERIC)". std::from_chars on Linux ignores the locale (https://en.cppreference.com/w/cpp/utility/from_chars: "Unlike other parsing functions in C++ and C libraries, std::from_chars is locale-independent, non-allocating, and non-throwing."; for floating point it "Expects the pattern identical to the one used by std::strtod in the default ("C") locale"). So a process-wide setlocale() with a comma-decimal locale (e.g. de_DE, pl_PL) would change config float parsing on macOS only: strtod would stop at the "." in "0.5", so strToNumber would return NUMERIC_PARSE_GARBAGE (follows from the man page; not measured). Hyprland's src/ has no setlocale call today (grep at the i18n step). Any setlocale() added in the port, or found in a later upstream file, must be flagged against this entry. tests/string/Numeric.cpp runs in the C locale and is not affected. hyprlang FLOAT values use std::stof (hyprlang src/config.cpp:481; https://en.cppreference.com/w/cpp/string/basic_string/stof: "Calls std::strtof(str.c_str(), &ptr)", decimal point "as determined by the current C locale"), which is locale-dependent on both platforms, so they're not affected by this entry; it applies only to hyprutils strToNumber users.

- File-name case (general, all file lookups): macOS volumes are usually case-insensitive (APFS; measured with pathconf(_PC_CASE_SENSITIVE) = 0 on the home volume /System/Volumes/Data and on /Volumes/Data; diskutil reports "APFS", not "Case-sensitive APFS"). No code change: Linux behaves the same on a case-insensitive filesystem, and a user on case-sensitive APFS gets Linux's behavior. Configs that work on Linux work unchanged on macOS; configs should use exact-case names so they stay portable back to Linux.

- hyprcursor-util -x (hyprcursor-util/src/main.cpp:229-376, converting XCursor themes) runs the external X11 tool xcur2png through popen; xcur2png isn't available on macOS (Homebrew has no xcur2png formula; brew info xcur2png: No available formula with the name "xcur2png"), so -x fails with its own message "missing dependency: -x requires xcur2png." - hyprcursor theme and shape order (UNVERIFIED): std::filesystem::directory_iterator order is unspecified and differs between APFS and ext4 (measured on APFS with ls -f on the test theme's cursors/: move.hlc, ll_angle.hlc, top_right_corner.hlc, xterm.hlc, ..., not alphabetical).
